WITS

An assistant that runs on my own machine and answers to me.

Follow a message through itCode on GitHub

What it is

WITS is a local-first assistant. I talk to it in a browser or on my phone. It plans, calls real tools, remembers context, and can edit its own code when asked. The models run on my own graphics card through Ollama, so nothing leaves the house unless I approve it.

This is the third version. The first two taught me what not to build.

How a message moves through it

  1. Arrive Everything anyone says comes in on one path.
  2. Route A list of plain checks runs in order. The first one that says yes decides where the message goes. Many messages never reach a model.
  3. Guard Injection patterns, personal-data patterns and the guest allowlist each get to say no.
  4. Work The orchestrator plans and calls tools, or hands off to a specialist: coding, book writing or self-repair.
  5. Answer One reply comes back, however many steps it took.

The router is ported to this site, with no model behind it, so you can type a message and watch the path it takes. Open Trace.

Decisions and what they cost

Local first.
The default models fit in about 8 GB of video memory. Small models are weaker, and I accept that. Asking a cloud model is possible, and it needs my approval each time. It is never automatic.
Route before you think.
Cheap checks in plain code come before any model call. That is faster and it is predictable: I can read why a message went where it did. The cost is phrase lists that have to be kept up by hand.
Edits have to prove themselves.
When WITS changes its own code, the change is written, the tests are run, and it is committed only if they pass. Otherwise the file goes back to its original bytes.
Guests get less.
Family can join on the home network with an invite code. They get chat and a filtered set of tools: no file writes, no self-repair, no settings.

What a review found

In November 2026 I reviewed the whole codebase against what I want it to become. The list was not flattering, and it is the plan now.

  • One model backend. Ollama is the only real one.
  • One shared secret. A single token guards every route. No scopes, and no way to cut off one client. The workspace changes this for outside agents: each gets its own token with its own limits, and I can revoke one without touching the rest.
  • Storage is JSON files. Fine for one user, unsafe once several agents write at once. The workspace is the first part on a real database, SQLite with migrations. The rest moves over in the foundations stage.
  • It only reacts. WITS acts when typed to. It has no calendar, mail, tasks or reminders.
  • Research code beside the hot path. About 6,000 lines of experiments live next to the code that answers messages.

Where it is going

  1. Measure the machine. Benchmarks before any building, so the plan rests on numbers. Done for the small models; the findings are below.
  2. A shared workspace. An MCP server where outside agents claim tasks, leave handoff notes and ask me for decisions. Approvals come to my phone, and I can cut off any one agent. This moved ahead of everything else because I can use it right away. It is built, and described in the next section.
  3. Foundations. A database in place of JSON files, more than one model provider, and a fast model and a heavy model with a router between them.
  4. Daily affairs. Tasks, reminders, a scheduler that starts work on its own, calendar and mail with approval before anything is sent.
  5. Agents out. WITS hands whole jobs to other coding agents as supervised workers, one graphics-card job at a time, and their results pass the same tested-edit rule.
  6. Voice. Local speech in and out.

Plan last updated November 21, 2026. The workspace is merged and running on my machine. A review of the whole thing passed it, with six fixes to make before real use. The last check is mine: approve a request from my phone, away from home Wi-Fi. The tool test has not yet been run on the two largest models.

The shared workspace

The first new piece is built. Other AI agents, on my laptop or anywhere on my private network, can connect to WITS and work on my projects alongside each other. They cannot do it quietly.

Five tools, and no more.
Read a project's state, claim a task, leave a handoff note, link a pull request or a file, and ask me to decide something. None of them runs code or touches a file on my machine.
A key for each agent.
Every agent gets its own token, limited to the projects and actions I choose. WITS keeps only a hash of it. I can revoke one agent and the others carry on.
Decisions come to me.
An agent that needs a yes or no files a request and keeps working. It shows up on an inbox page on my phone, with a push if I want one. Approving records my answer. It does not run anything.
What agents write is data.
Text from an agent is cleaned of invisible characters, checked against known injection patterns, flagged if it matches, and shown as plain text. Every tool tells the agent reading it to treat that text as data, not instructions.
Everything is logged.
Each call leaves one audit row: who made it, what it was, which project, and how it ended.
Not on the internet.
The endpoint is reachable only over a private network between my own devices. Nothing is opened to the outside.

What measuring found

The machine is a mid-range desktop: an RTX 3070 with 8 GB of video memory, a six-core i5-12400F and 32 GB of DDR4. Before building anything I had a benchmark written and ran every model I keep. One day of measuring changed the plan more than a week of reading would have.

  • A stick in the wrong slot cost a quarter. Three mismatched sticks sat with 8 GB on one memory channel and 24 GB on the other. Moving one balanced them, and both large models ran about 25% faster. It cost nothing.
  • The readout was wrong. Ollama reported one large model as 82% on the graphics card. Its own log showed 3.8 GB on the card and 13.2 GB in system memory. I go by the log now.
  • A newer engine beat the convenient one. llama.cpp added a cache that keeps the busiest parts of a mixture-of-experts model on the graphics card. On this card it took the largest model from 36 to about 46. That is two short runs on one prompt, so I expect less in mixed use.
  • Fast is not the same as dependable. A second test replays 36 fixed tool-calling cases and scores them in code, with no model as judge. Among the small models, the most reliable got 89% right. The fastest answered in about a quarter of a second and got 75%.
  • The test had bugs of its own. The first run turned up a tool description that YAML had silently mangled, and a few cases that were unfair to every model. The cases were fixed and the run repeated before any score counted.
  • Small models give up politely. When a tool call failed, the small models mostly told me so and stopped. They did not try again. That is safe, and it means retries belong in my code, not in the model.

Full tables, the exact commands and the caveats are in the repository's benchmark notes.

What the second review caught

WITS is built the way I run all my larger projects: I set the design and the standards, and AI agents write much of the code under them. The standards have a page of their own, How I work. One of them is that anything touching access gets a second, independent security review. Here is what that review did on this project.

It refused the first design contract for the workspace and listed seven security defects. One would have let an agent close tasks in a project it had no access to. Another left room for an agent to approve its own request. All seven were fixed before I would build on it.

The token code got the same second review. It found no way for a token to leak. It did find that the test meant to prove a token never reaches the logs could not fail. The test was fixed, then shown to fail on a deliberate leak, before the change went in.

The same review ran on every part that touches access. It kept finding real problems, which is the point of it.

  • A dropped connection could split a write from its record. A revoked agent could have been left holding a task, or a change could have landed with no audit entry. The write, the check and the record now finish together.
  • One injection check was slow on purpose-built input. A crafted message took over a second to scan. Rewritten to match the same text, the check takes under a millisecond.
  • An agent could write into a log another agent reads. Text of its choosing would have reached the file the self-repair agent works from. Those requests are now refused without recording what was sent.
  • A link could lie about where it goes. An address written as a trusted site followed by an at sign and another host would have looked safe on my phone. It is refused.

The last review covered the whole workspace at once. It built the real application, connected a real MCP client, and walked the full path: create an agent, claim a task, ask for a decision, approve it, revoke the agent. It passed, with six more fixes to make first.

How it is built

  • Core: Python, with a FastAPI web app that also installs on a phone.
  • Models: Ollama, with separate small models for general work, coding and embeddings.
  • Tools: about 30 built in and discovered at start-up, plus outside tools over MCP.
  • Agents in: an MCP endpoint with five tools, a token for each agent, and SQLite behind it.
  • Memory: a FAISS vector index beside the session records.
  • Tests: more than 1,100 in pytest as of November 2026, run by GitHub Actions on two versions of Python.
