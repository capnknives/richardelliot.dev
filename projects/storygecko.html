StoryGecko

A story bible that keeps up with your manuscript.

The code is private while testing is under way.

The problem

Long fiction outgrows its author's memory. Eye colors drift, a side character's job changes between chapters, a thread opened in chapter three never closes. Writers keep a story bible to hold all of that, and keeping it current is a second job.

Where it came from

The idea is older than the app. In May 2025 I built a first attempt called Storyforge. It had the screens: a dashboard, an upload page, outlines and character lists. What it did not have was anything behind them that could read a whole book and get the facts right. I did not know how to build that yet, so I shelved it and kept learning.

I came back in November 2026 and started over as StoryGecko. The first thing built was the part the prototype never had: the pipeline that reads a real manuscript, tested on my own novella from the first day.

What it does

  • Reads the book. Upload a manuscript or write in the built-in editor. It drafts the story bible: outline, characters and relationships.
  • Asks instead of guessing. Anything uncertain or contradictory goes to a review queue for the writer to settle.
  • Answers with quotes. Ask your book a question and the answer comes with the lines it rests on, each one clickable.
  • Checks continuity. On request, it flags where a chapter contradicts what the rest of the book says.
  • Suggests, from where you are. “What happens next” offers three directions from the cursor, using only what a reader would know by that page.
  • Keeps your words safe. Autosave, revisions, a 30-day trash, offline writing, and export to .docx, .md, .txt or a full backup.

How a book moves through it

  1. Upload or write The web app sends the text to the API.
  2. Store and queue The API saves it and queues a job. It never waits on a model.
  3. Read A background worker reads one chapter at a time and caches each reading.
  4. Merge Plain code, no model, merges the readings into one bible.
  5. Review What the merge could not settle goes to the writer.
  6. Agree The bible changes only when the writer says yes.

Decisions and what they cost

It reads your book. It never writes it.
No rewriting a selection, no generated scenes, no voice imitation. Critique drops any note that offers replacement wording. The cost is a feature most writing tools sell first. I decided the writer stays the author.
Nothing updates on its own.
The bible refreshes when the writer agrees, and checks run on request. The cost is a bible that can fall behind the text, so the app shows when it is stale instead of hiding it.
No quote, no answer.
An answer with no line from the book that checks out is replaced by “couldn't find words in the book that answer this.” In a blind review, the answers without quotes were the wrong ones.
Facts are stamped by chapter.
Every fact records where it becomes true. A suggestion at chapter 12 only sees chapters 1 to 12, so the tool cannot leak a twist the reader has not reached. It makes every query more work.
One database.
Postgres holds the data and the job queue, with room for embeddings when they are needed. There is no Redis, no graph database and no separate vector store to run. The page polls for finished work instead of getting it pushed.
Own sign-in, own model clients.
No hosted identity service and no orchestration framework. That keeps a writer's book in one place and the moving parts readable. It also means sessions, rate limits and retries were mine to get right.

What testing found

Story bible accuracy on a 13,000-word novella, scored against a 38-point answer key. Same prompts and same code for both models. November 9, 2026.
Small local model, 8 GB graphics card22 / 38
Large cloud model37 / 38

The model, not the pipeline, is the main limit on accuracy. So the plan has two tiers: a free local model that keeps the book on your machine, and a stronger model for writers who want it, on a metered plan or their own key. The answer key stays as the regression test.

  • A checker that runs is not a checker that works. The first continuity run on the local model raised six confident flags. All six were false. Flags now need an exact quote of four or more words and a problem that says more than the fact itself. That run dropped to zero.
  • Recall is still low. With the stronger model, the checker caught 1 of 13 known issues in the test book. It is honest about what it finds and it misses a lot. That is the next thing to fix.
  • A lost-update bug, found by writing a test. Two saves arriving together could both succeed, and the later one replaced the earlier one's words. One conditional update now claims the version. The test that found it stays in the suite.

How it is built

  • Web: Next.js and TypeScript, with a Tiptap editor. Installable, and it keeps working offline.
  • API: Python and FastAPI. Accounts, uploads, the editor and the assistant routes.
  • Worker: a Python process that claims jobs from the Postgres queue and calls the model.
  • Data: Postgres with pgvector, SQLite for local runs, schema changes as Alembic migrations.
  • Models: a local model through Ollama, or Anthropic's API, behind one small interface.
  • Tests: more than 300, in pytest and in a real browser with Playwright, run by GitHub Actions on every change. A rule-based fake model lets the browser tests run the real pipeline.

The first eight days were 36 pull requests, each with its notes in a build log: what was built, how long it took, and what broke. I work with AI coding agents and direct them. I set the rules above, test on my own book, and decide what ships.

Where it is going

The bible is one document while its shape settles. It will be split into tables for entities, facts and relationships once the continuity checker needs to query them. After that: a desktop app, billing, branching stories, and writer essentials like focus mode, word goals and EPUB export.

The code is private while testing is under way. Screenshots will follow when the app is ready to be shown.
