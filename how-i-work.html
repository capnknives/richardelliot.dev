Who writes the code

On my larger projects I work as the lead: the architect and the reviewer. I set the design and the standards, and AI agents write much of the code under them. Riftforge is the exception among the large projects. I wrote a good deal of specific code for it myself, as a learning exercise.

I spent years writing scripts by hand for MUDs and game automation, none of it kept. Today I mostly direct AI agents and review what they write. The pool water balance calculator on this site is an agent rebuild of one I first wrote myself, from my own chemistry rules.

Whoever writes a change, I hold it to the same engineering standards before I accept it.

The standards

  • Design before code. Interfaces and data shapes are agreed in a written contract first, so parts built separately fit together.
  • Small, reviewable changes. One purpose per pull request, small enough to read in full. Each is reviewed against its brief, and nothing merges without me.
  • Tested, or it does not ship. Every change carries its own tests. The full suite and the linters run automatically on each pull request.
  • Efficient by default. I check how the work grows with the data: indexed lookups instead of scans, capped result sizes, and nothing slow inside a step that runs on every request.
  • Built to grow. Modules stay small and every write has one clear owner, so more users do not mean a rewrite. In WITS that meant moving storage from loose files to a database with migrations.
  • Secure by design. Least access by default, and credentials that can be revoked one at a time. Secrets stay out of the code, and anything that touches access gets a second, independent security review.
  • Private by default. Personal data stays where its owner put it unless they say otherwise. In WITS it stays on my machine, and nothing leaves the house without my approval. This site keeps nothing about its visitors.
  • Measured, not assumed. Performance claims come from benchmarks I can run again, written down with their limits.
  • Fails safe. A change that breaks the tests does not land, and risky actions wait for my approval.
  • Documented as it goes. Plans, decisions and results live in the repository beside the code.

The standards at work

A list like this is easy to write. The WITS case study has two times it earned its keep: a design contract the second reviewer refused, with seven security defects in it, and a test that could not fail.
